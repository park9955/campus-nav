## 2. 기존 비즈니스 프로세스

### 2.1 자산 관리 프로세스 (현황)

**자산 검색 및 조회 프로세스:**
```
사용자 로그인 → 검색 조건 입력 (키워드/카테고리/상태)
  ↓
SearchServlet → 데이터베이스 조회
  ↓
자산 목록 표시 (searchAssets.jsp)
  ↓
자산 선택 → DetailServlet → 상세정보 조회 (detail.jsp)
```

**자산 예약 프로세스:**
```
자산 상세정보 화면 → 예약 버튼 클릭
  ↓
ReserveServlet → 중복 검사 → 데이터베이스 저장
  ↓
예약 완료 (reserve.jsp)
```

**자산 이관 프로세스:**
```
이관 요청 페이지 (transfer.jsp) → RegisterServlet
  ↓
신청서 작성 → 데이터베이스 저장
  ↓
조교/관리자 승인 대기
  ↓
승인/반려 (asset_manage.jsp)
```

### 2.2 역할별 사용 프로세스

| 역할 | 주요 프로세스 | 사용 도구 (현황) | 빈도 |
|------|-------------|--------------|------|
| **학부생** | 자산 검색/예약, 내비게이션 조회 | 웹 시스템 | 주 2-3회 |
| **조교** | 자산 예약 승인, 이관 검증, 이력 조회 | 웹 시스템 | 주 1회 |
| **교수** | 교과목/스킬 정보 관리 | 웹 시스템 | 월 1회 |
| **관리자** | 전체 자산 관리, 폐기 처리, 권한 제어 | 웹 시스템 | 일일 |
| **게스트** | 자산 검색(읽기 전용) | 웹 시스템 | 수시 |
| **방문객** | 내비게이션 조회만 가능 | 웹 시스템 | 수시 |

### 2.3 데이터 흐름 (현황)

```
[사용자 로그인]
    ↓
[LoginServlet - 권한 검증]
    ↓
[Session 생성 - 역할 저장]
    ↓
[역할별 메인 페이지 표시]
    ↓
[기능별 Servlet 호출]
    ├─ SearchServlet (자산 검색)
    ├─ ReserveServlet (예약)
    ├─ RegisterServlet (이관/등록)
    ├─ DetailServlet (상세정보)
    └─ GuestServlet / VisitorServlet (제한 접근)
    ↓
[MySQL 데이터베이스 CRUD 작업]
    ↓
[JSP 페이지 렌더링 및 응답]
```

## 3. 기존 시스템 구조 분석

### 3.1 기술 스택 및 구성

**백엔드 (Server-side):**
- **언어:** Java 11 LTS
- **프레임워크:** Servlet/JSP (레거시 Struts2 미사용)
- **서버:** Apache Tomcat 9.x
- **데이터베이스:** MySQL 8.x

**프론트엔드 (Client-side):**
- **HTML/CSS:** Bootstrap 5.3.3
- **JavaScript:** Vanilla JS (jQuery 미사용)
- **UI 패턴:** MVC 기반 요청-응답 모델

**버전 관리:**
- **VCS:** Git/GitHub
- **협업:** GitHub Issues, Discussions


## 4. 시스템 문제점

### 4.1 비즈니스 레벨 문제점

| ID | 문제점 | 영향도 | 현황 |
|----|--------|--------|------|
| **P-001** | 자산 관리가 분산된 엑셀/수기 기록으로 이루어짐 | 높음 | 새 시스템으로 전환 중 |
| **P-002** | 자산 위치, 상태, 예약 정보가 실시간 동기화 불가 | 높음 | 중앙 DB로 해결 |
| **P-003** | 층별 위치 파악이 어려워 찾는 데 시간 소요 | 중간 | 3D 맵 내비게이션 개발 중 |
| **P-004** | 자산 이관/폐기 이력 추적 불가 | 높음 | audit_log 테이블로 구현 예정 |
| **P-005** | 교수 정보 관리 프로세스 부재 | 중간 | 교수 관리 모듈 기획 중 |

### 4.2 기술 레벨 문제점

| ID | 문제점 | 원인 | 영향도 |
|----|--------|------|--------|
| **T-001** | 레거시 Servlet/JSP 스택 유지 | 기술 스택 고정 정책 | 높음 (개발 속도 저하) |
| **T-002** | MVC 패턴의 느슨한 구현 | Controller/View 경계 모호 | 중간 (유지보수성) |
| **T-003** | 자동화된 테스트 프레임워크 부재 | 초기 개발 단계 | 높음 (품질 검증 어려움) |
| **T-004** | 성능 최적화 미흡 (인덱싱, 캐싱) | 아직 구현 초기 | 중간 (향후 병목 가능성) |

| **T-006** | 에러 처리 및 로깅 불일관 | 표준화된 가이드 부재 | 중간 (디버깅 어려움) |

## 5. 사용자 기대 및 요청사항

### 5.1 사용자 니즈 분석

**학부생:**
- ✓ 필요한 자산을 빠르게 검색 (< 2초)
- ✓ 자산 예약/취소 편의
- ✓ 캠퍼스 내 자산 위치를 쉽게 파악 (3D 맵)
- ✓ 이용 가능 시간 확인
- ✓ 예약 이력 조회

**조교:**
- ✓ 자산 이관 요청 검증 및 승인
- ✓ 자산 이력 추적
- ✓ 자산 상태 변경 관리
- ✓ 전체 자산 목록 조회

**교수:**
- ✓ 교과목 및 스킬 정보 입력/수정
- ✓ 담당 교과목 목록 조회
- ✓ 캠퍼스 내비게이션

**관리자:**
- ✓ 전체 자산 관리 (등록/수정/삭제)
- ✓ 사용자 권한 제어
- ✓ 자산 폐기 처리
- ✓ 시스템 모니터링
- ✓ 감사 로그 조회

**게스트:**
- ✓ 자산 검색 (읽기 전용)
- ✓ 캠퍼스 내비게이션

**방문객:**
- ✓ 캠퍼스 내비게이션만 가능

### 5.2 주요 요청사항

| 요청사항 | 담당 역할 | 우선순위 | 상태 |
|---------|---------|---------|------|

## 7. 내부 데이터 연계 활용

### 7.1 데이터 출처 및 연계

**주요 데이터 소스:**

| 데이터 | 출처 | 형식 | 빈도 | 용도 |
|--------|------|------|------|------|
| 자산 정보 (8,401개) | 기존 DB / mysql에다넣고실행_fixed.sql | SQL Dump | 초기 로드 | 자산 검색, 예약, 예약 |
| 사용자 정보 | 교내 인사 시스템 (연계 예정) | LDAP/CSV | 월 1회 | 인증, 역할 매핑 |
| 층별 지도 | 시설팀 제공 | PNG/JPG | 1회 | 내비게이션 맵 |
| 교수 정보 | 교무시스템 (연계 예정) | CSV | 학기 시작 | 교수 프로필, 교과목 |
| 예약 정보 | 시스템 생성 | DB | 실시간 | 자산 가용성 관리 |

### 7.2 데이터 통합 전략

```
[교내 시스템들]
├─ 인사 시스템 (사용자, 역할)
├─ 교무 시스템 (교수, 교과목)
└─ 시설 시스템 (층별 지도)
        ↓
[데이터 마이그레이션 / ETL]
├─ 초기 로드: mysql에다넣고실행_fixed.sql 실행
├─ 주기 동기화: 스케줄 배치 작업
└─ 실시간 연계: (Phase 2 이후 고려)
        ↓
[CAN MySQL Database]
├─ assets (8,401개 자산)
├─ users (인사 시스템 연계)
├─ professors (교무 시스템 연계)
└─ floors (시설팀 제공 맵)
        ↓
[웹 애플리케이션]
└─ 통합 검색, 예약, 이관, 내비게이션
```

### 7.3 데이터 품질 관리

**초기 데이터 검증:**
- 중복 제거
- NULL 값 확인
- 데이터 타입 검증
- 외래키 정합성 검증

**운영 중 데이터 관리:**
- 주기적 감시 및 정제 (월 1회)
- 감사 로그를 통한 변경 이력 추적
- 백업 정책 (일일 증분, 주간 전체)

## 9. 결론 및 권고사항

### 9.1 현황 종합 평가

**강점 (Strengths):**
- ✓ 명확한 프로젝트 목표 및 범위 정의
- ✓ 기술 스택이 안정적이고 오픈소스 기반
- ✓ 핵심 모듈 (인증, 검색, 예약)의 초기 구현 완료
- ✓ 8,401개 자산 데이터 사전 준비

**약점 (Weaknesses):**
- ✗ 레거시 Servlet/JSP 스택으로 인한 개발 속도 저하 가능성
- ✗ 자동화 테스트 프레임워크 부재로 인한 품질 검증 어려움
- ✗ 데이터 정합성 및 성능 최적화 미확인
- ✗ 보안 검증 프로세스 미흡

**기회 (Opportunities):**
- ◐ 내비게이션 3D 맵 구현으로 경쟁력 확보
- ◐ 역할별 맞춤형 인터페이스로 사용자 만족도 향상
- ◐ 감사 로그를 통한 완전한 추적성 확보
- ◐ 향후 REST API 제공으로 외부 연계 가능성

**위협 (Threats):**
- ⚠ 2026-07-31 배포 기한의 촉박성 (2개월)
- ⚠ 기존 자산 데이터의 정합성 미확인
- ⚠ 동시 100명 사용자 처리 성능 미검증
- ⚠ 보안 취약점 (SQL Injection, XSS 등) 위험

### 9.2 권고사항

**Phase 1 (분석 & 설계 단계):**

1. **데이터 검증 우선화**
   - 8,401개 자산 데이터 정합성 검증 스크립트 작성
   - 중복/오류 데이터 정제 계획 수립
   - 데이터 마이그레이션 리스크 평가

2. **보안 기준선 설정**
   - PreparedStatement 필수 사용 정책 수립
   - 입력 검증 및 XSS 필터 표준화
   - 코드 리뷰 체크리스트에 보안 항목 추가

3. **테스트 전략 수립**
   - BDD 시나리오 작성 기준 정의
   - 단위/통합/E2E 테스트 자동화 계획
   - 성능 테스트 기준값 설정

4. **개발 문서 표준화**
   - 아키텍처 설계 문서 작성
   - API 문서 자동 생성 방안 검토
   - 개발자 가이드 작성

**Phase 2-5 (구현 단계):**

5. **주간 마일스톤 관리**
   - 2주 단위 진행률 리뷰
   - 위험 요소 조기 감지 및 대응
   - 스코프 변경 엄격히 관리

6. **품질 관리 강화**
   - 코드 커버리지 > 80% 목표
   - 보안 취약점 스캔 자동화 (OWASP Top 10)
   - 성능 테스트 (응답 시간, 동시 사용자)

7. **사용자 교육 준비**
   - 역할별 사용 설명서 작성
   - 비디오 튜토리얼 제작
   - 시범 운영(Pilot) 계획 수립

**Phase 6 (배포 & 운영 단계):**

8. **배포 준비**
   - 롤백 계획 수립
   - 모니터링 대시보드 구성 (로그, 성능, 에러)
   - 운영 매뉴얼 작성

9. **지속적 개선**
   - 사용자 피드백 수집 및 분석
   - 월간 성능 리뷰 및 최적화
   - 향후 기능 로드맵 수립 (이메일 알림, API, 등)
