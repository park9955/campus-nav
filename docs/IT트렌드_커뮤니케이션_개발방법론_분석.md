## 1장. IT 트렌드: 레거시 vs 현대 기술 스택

### 1.1 현대 웹 개발 트렌드 (2024-2026)

2024년 기준 웹 개발 생태계는 다음 네 가지 트렌드로 정리된다:

1. **마이크로서비스 아키텍처 (Microservices)**: 단일 대형 애플리케이션을 작은 독립적 서비스로 분해
2. **클라우드-네이티브 개발 (Cloud-Native)**: Kubernetes, Docker 기반 자동 배포/확장
3. **저코드/노코드 플랫폼 (Low-Code/No-Code)**: 개발자 없이 기업 로직 구현
4. **AI/ML 통합 개발 (AI-Driven Development)**: LLM 기반 코드 생성, 테스트 자동화

### 1.2 CAN 프로젝트의 기술 선택: 왜 Servlet/JSP인가?

**현황:** CAN은 Java 11 + Apache Tomcat 9.x + MySQL 8.x 기반 Servlet/JSP 아키텍처 선택

**선택 이유 (ADR 분석):**

| 트렌드 기술 | CAN 미선택 사유 |
|-----------|---------------|
| **Spring Boot** | 기술 스택 고정, 추가 의존성 불필요, 개발 속도 우선 |
| **Kubernetes** | 온프레미스 단일 서버(Windows 11), 오버헤드 과다 |
| **Node.js/React** | 팀 역량(Java 개발자 2명), 학습곡선 |
| **AWS/GCP** | 예산 제약($0), 교내 인프라 활용 |

**결론:** "필요한 기술만" 원칙에 따른 합리적 선택

### 1.3 레거시 기술의 역할과 가치

**레거시 = 구식 ≠ 무가치**

- ✓ **안정성**: Servlet/JSP는 25년 검증된 표준
- ✓ **유지보수성**: 간단한 구조 → 새로운 개발자 학습 용이
- ✓ **비용**: 무료 오픈소스, 라이선스 비용 0원
- ✗ **한계**: 현대 DX(Digital Transformation) 요구에 미흡

**트렌드와의 조화:** CAN의 로드맵에서 **Phase 6(2026년 8월)부터 REST API 도입**, **Phase 7(2026년 10월)부터 모바일 앱(Vue.js) 병렬 개발** 계획

## 2장. IT 커뮤니케이션: 문서 기반 협업

### 2.1 왜 "문서"인가? 

전통적 커뮤니케이션의 한계:
- 👤 개발자 A: "예약 기능 어디 구현해요?"
- 👥 팀: "search.jsp에... 아니 reserve.jsp에..." (혼란)

**CAN의 해결책: 설계 문서 우선주의 (Design-First)**

CAN 프로젝트의 `docs/` 폴더 구조:
```
docs/
├─ 01기획서_aisw.md          [무엇을 만드나?]
├─ 02현황분석서_aisw.md      [현재 상태는?]
├─ 02요구사항명세서_aisw.md  [기능 정의: FR-001, FR-002, ...]
├─ 03_시스템아키텍처설계서_aisw.md   [어떻게 구조화?]
├─ 03_데이터설계서_aisw.md   [DB 스키마는?]
├─ 개발방법론_aisw.md        [개발 규칙은?]
└─ 아키텍처결정기록(ADR)     [왜 이 기술?]
```

**효과:** 모든 팀원과 AI 에이전트가 같은 context에서 작업

### 2.2 BDD (Behavior-Driven Development) 실무 적용

**BDD = 사용자 관점의 테스트 작성**

CAN 예시:

```gherkin
# Feature: 자산 검색
Scenario: 키워드로 자산 검색
  Given 데이터베이스에 "프로젝터" 2개가 저장되어 있다
  When 사용자가 "프로젝터"로 검색한다
  Then 2개의 검색 결과가 반환된다
  And 각 결과는 "프로젝터"를 포함한다
```

**BDD의 가치:**
1. **명확성**: 요구사항 ↔ 테스트 ↔ 코드 일대일 매핑
2. **추적성**: 버그 발생 시 "어떤 시나리오 실패인가"로 즉시 파악
3. **문서화**: 테스트 = 최신 문서 (자동 갱신)

**CAN의 현황:** BDD 미도입 (Phase 2 우선순위 #1)

### 2.3 ADR (Architecture Decision Records): 기술 결정 기록

**문제:** "왜 MySQL 선택했어?" → 6개월 뒤 담당자가 떠나면 의도 소실

**해결책: ADR 문서화**

CAN 예시 - **ADR-001: Servlet vs JSP 책임 분리**

```markdown
## 결정
인증은 Servlet, 데이터 처리는 JSP에서 직접 JDBC 호출

## 이유
- 복잡한 비즈니스 로직 없음 (CRUD 중심)
- 빠른 개발 속도 필요
- 작은 팀(2명) 규모에 적합

## 대안
- A1: 모든 처리를 Servlet에서 → 복잡도 ↑
- A2: 순수 MVC (DAO/Service 계층) → 초기 속도 ↓

## 결과
→ 채택, 새 Servlet 추가 시 web.xml 등록 필수
```

**효과:** 6개월 뒤 신입 개발자도 "왜 이 구조인지" 이해 가능

## 3장. 개발방법론: Layered Architecture와 AI 협업

### 3.1 Layered Architecture (3계층 구조)

CAN의 아키텍처:

```
┌─────────────────────────────┐
│  표현 계층 (View)            │
│  ├─ JSP (30+ 페이지)        │
│  └─ 정적 자산 (CSS/JS)      │
├─────────────────────────────┤
│  비즈니스 로직 (Controller)  │
│  ├─ Servlet (10개)          │
│  ├─ Filter (보안/권한)      │
│  └─ Utility (공통 함수)    │
├─────────────────────────────┤
│  데이터 접근 (Model)         │
│  ├─ DAO (8개)               │
│  ├─ DBUtil (연결 관리)      │
│  └─ MySQL (8,401개 자산)   │
└─────────────────────────────┘
```

**각 계층의 책임 (Single Responsibility Principle):**
- **View**: 데이터 출력만 (비즈니스 로직 금지)
- **Controller**: 입력 검증 + 권한 확인 (DB 접근 금지)
- **Model**: DB 쿼리만 (UI 로직 금지)

**장점:** 한 계층의 변경이 다른 계층에 영향 최소

### 3.2 추적성 (Traceability): FR-ID 기반 개발

**요구사항 → 코드 → 테스트의 일관성 유지**

CAN 실행 예시:

**Step 1: 요구사항 명세**
```markdown
| FR-001 | 자산 검색 | 키워드/카테고리/상태 필터링 |
| FR-002 | 예약 중복 방지 | UNIQUE 제약 + AJAX 검사 |
```

**Step 2: 코드에 ID 기록**
```java
// FR-001: 자산 검색 기능
public List<Asset> searchAssets(String keyword, String category) {
    // SearchServlet에서 호출
}
```

**Step 3: 커밋 메시지에 포함**
```
commit: "FR-001: 자산 검색 필터링 구현 - 키워드/카테고리 지원"
```

**Step 4: 버그 추적**
```
Issue: search.jsp 결과가 NULL
→ git log --grep="FR-001" → 최근 변경 사항 파악
→ 코드 리뷰 → 쿼리 오류 발견 → 수정
```

**효과:** 6개월 뒤 "이 코드가 뭐 하는 거지?"라는 질문 없음

### 3.3 AI 에이전트 협업 방법론

**핵심 원칙: "텍스트 명확성 = 코드 품질"**

CAN의 예시 - AI 에이전트에 지시하기:

**❌ 나쁜 예 (모호함):**
```
"SearchServlet 고쳐줘. 뭔가 이상해"
```
→ AI: "뭘 고치는지 모르겠는데요?"

**✅ 좋은 예 (명확함):**
```
"FR-001: 자산 검색 기능
현상: search.jsp에서 카테고리 필터 미적용
기대: SearchServlet에서 category 파라미터 받아서
      "실험 장비"만 필터링해야 함
아키텍처: Layered 구조, DBUtil.getConnection() 필수 사용
데이터: MySQL assets 테이블, category 컬럼 타입=VARCHAR(100)
테스트: INSERT로 테스트 데이터 생성 후 search.jsp?category=실험장비 접속"
```
→ AI: 정확히 수정 가능

**AI 협업의 4가지 요소:**
1. **설계 문서 = 입력**: 아키텍처 설계서, 데이터 설계서 읽음
2. **명확한 지시사항**: "이 부분 고쳐" (X) → "FR-001 기능 추가" (O)
3. **피드백 루프**: "안 맞네" → 문서 업데이트 → 재시도
4. **추적 가능성**: 모든 코드 변경이 요구사항과 연결

## 결론: 세 요소의 통합

| 요소 | CAN 실행 | 효과 |
|-----|--------|------|
| **IT 트렌드** | 필요한 기술만 선택 (Servlet/JSP) | 학습 시간 ↓, 개발 속도 ↑ |
| **IT 커뮤니케이션** | 문서 + BDD + ADR 기반 협업 | 의도 손실 ↓, 일관성 ↑ |
| **개발방법론** | Layered + 추적성 + AI 협업 | 유지보수성 ↑, 오류 ↓ |

**2026년 7월 배포 성공의 열쇠: 기술이 아니라 "소통"과 "명확성"**
